# Local single-radiologist series review

Isolated research prototype, **not validated for diagnostic use**. Production assessments are stored in **Firebase Firestore, project genai-radiology, collection afrooz-review**, not on the Mac. Images remain on the researcher Mac; the Mac is still required for image decoding and server-side assessment writes. No CDN assets or telemetry. The server binds **127.0.0.1 only**. Local access has no authentication: other users/processes on this computer can access it; the token is CSRF protection, not authentication. Never forward this port directly or use it for multi-user review. Password-protected remote HTTPS access is described in [orthanc/HTTPS.md](orthanc/HTTPS.md). DICOM pixels may contain burned-in information: neutral labels do **not** make them anonymized.

**Operational note (current rollout):** Rubric v4 is deployed at https://genai-radiology-verify.web.app/ and authenticated remote reviewing is enabled. Both remote review and the local UI use production Firestore storage; neither is an isolated test environment. Refresh existing tabs after a backend restart.

## Run locally

Requires Node 20+ and a Python environment with the packages listed in requirements.txt. No Node package installation or monorepo build is required. The default interpreter is the existing Downloads/.trajectory-dicom-venv/bin/python; override with REVIEW_PYTHON if necessary. Run these from the repository root:

- First-time freeze: `node review-app/prepare.mjs`
- Optional one-time private prompt enrichment after freezing: `node review-app/prepare-prompts.mjs` (existing gcloud login required; never run automatically by the server).
- Start: `node review-app/server.mjs`
- Production CLI startup defaults to Firestore, including when using the local UI. A valid server-side gcloud login with access to the project is required; see storage operations below. Imported `startServer()` defaults to isolated local storage for tests.
- Open **http://127.0.0.1:4318**. Stop with Ctrl+C.
- Tests: `node --test review-app/server.test.mjs review-app/browser.test.mjs`
- All-source decode validation: run the configured Python interpreter with `review-app/pixels.py --validate review-app/.private`.

Preparation reads only the existing Downloads/explanation-trajectory-report.html embedded snapshot and Downloads/trajectory-dicom-series.json, never the live report generator or Firestore. It freezes the exact 29 unique StudyUID + SeriesUID targets inside schedule-start-inclusive/end-exclusive windows, restricted to the two approved studies. It requires exactly 28 exact local matches, and refuses duplicate SeriesUIDs, duplicate SOPs, mismatched source counts, and overwrite. The unmatched target is retained privately but is **not** a review case. No source/control series are added or duplicated. Case ordering is fixed and neutral, not randomized. Local source files are never modified.

The two source roots are the approved `{uid} Generated Patient {uid}` folders in Downloads. The private manifest fixes every permitted path and frame number; HTTP requests accept case IDs and bounded frame indices, never paths. At startup the SHA-256 manifest seal, uniqueness, and canonical path allowlist are checked. Pixels are decoded by pydicom in a persistent local worker; source study, series, and SOP identities are checked at each decode. Missing, changed, or unsupported images fail explicitly. The seal detects accidental changes, not malicious local editing; pixel contents themselves are not cryptographically frozen.

Preparation refuses to replace a freeze. Do not delete/rebuild an existing cohort when reviews exist. An interrupted preparation may leave partial files: inspect them and move that entire private directory aside before starting over. REVIEW_PRIVATE_DIR can select a separate private folder; if outside the ignored defaults, keep it outside version control. REVIEW_PORT changes only the port, never the bind address.

## Prompt provenance

Prompt enrichment does not replace or reseal the frozen manifest. It verifies the local index hash and exact strict-window target set against that manifest. A regenerated report is permitted only with the same targets; both report hashes and the exact schedule windows are retained privately. The current report uses the same fixed study schedule as the cohort freeze.

Firestore has no composite index for study + time. To avoid any cloud writes, the enrichment first projects only timestamp/study/series identifiers for the two approved studies. It then reads **prompt fields only for exact frozen case pairs inside schedule-start-inclusive/end-exclusive windows**, using masked batch reads. No answers, patient metadata, or unrelated prompt texts are retrieved. Each case's event count must match the report snapshot. Access tokens stay in process memory; no credentials are saved or printed. The one-time output is sealed, read-only, ignored private metadata, not a public report.

Important: `createPrompt` constructs `promptText` from the variation form answers; `GenerationOptions` passes `promptKey` to `findBestMatchingDisplaySet` and logs the selected existing series. This code path does **not** generate pixels or prove the exact original model input. Therefore the main display uses the local **DICOM series description (generation prompt not verified)**, rather than relabeling a logged matching input as an original generation prompt. Expandable details list **all distinct logged input prompts**, matched by exact study + series and strict windows. No arbitrary input is selected when several map to one series. If the local description is missing or ambiguous, the UI says so and does not invent a caption.

For this frozen cohort: all 28 cases have one DICOM description and logged inputs; three cases have multiple distinct logged inputs. In 27 cases at least one logged input is not text-identical to the DICOM description. All logged series descriptions agree with the local descriptions. Text differences are not automatically clinical contradictions, and this analysis does not verify original generation captions. Description matching is against the single displayed DICOM description, not every alternative logged input. Clinical accuracy is assessed independently of that description.

## Viewer and assessment

- OHIF-matching navy chrome, blue active-viewport border, and cyan accents use the repository's OHIF UI palette. This is still a standalone local canvas renderer, **not the OHIF engine**. All icons are inline SVG; system fonts require no external requests. Desktop queue and assessment panels scroll independently; phone layouts place the review below the image with document scrolling.
- The toolbar's Window / level, Pan, and Zoom buttons stay synchronized with the original Drag tool select. With the viewport focused, **W / P / Z** select those tools and **R** resets the view. Shortcuts do not intercept typing in the review form. Original presets, retry, reset, and zoom controls remain available. Static UI assets are read at server startup: restart the local server after editing them; do not rebuild the frozen cohort or remove ratings.
- Entire manifest-listed series is scrollable: wheel, arrow keys in the viewport, slider, or slice buttons. Full-resolution decoded slices preload nearest-first in the background (at most two transfers at a time). Waiting now fills an in-memory cache for the active stack, rather than only loading slices after scrolling stops. Cached slices display immediately without blanking; uncached navigation is throttled rather than debounced so continuous scrolling cannot indefinitely postpone loading.
- The active-stack pixel cache is bounded to 128 MiB (this cohort's 256 × 256 × 256 float32 stack is 64 MiB). Larger stacks retain a nearby window instead of endlessly cycling downloads. Switching cases/signing out clears the cache; no browser persistent storage or service worker is used. The status shows slices cached **in this tab**, separately from cumulative successful loads; neither means visual inspection. Background failures remain explicit, with failed slice numbers and a button to retry all failed transfers without losing the current position. Foreground transfers have a 30-second timeout.
- Local window/level drag, DICOM/lung/soft-tissue/bone/range presets, pan, zoom drag/buttons, reset, and in-session per-case viewport restoration. Frame swaps are invalidated immediately on selection and stale asynchronous responses are ignored; old pixels are cleared during loading/errors.
- Grayscale MONOCHROME1/2, modality LUT/rescale, linear windowing, and pixel aspect ratio. Multiframe files are frame-indexed. Files sort by patient-plane projection when consistent geometry is available, otherwise by InstanceNumber (explicit warning). No anatomical orientation labels or diagnostic measurements are asserted.

### Current rubric v4

The authoritative questions, definitions, choices, and conditional issue tags are in [rubric.mjs](rubric.mjs). Two independent questions start unanswered; both require an explicit choice to finalize. Any combination of the two answers is valid. There is **no “unable to assess” option**, and no answer is filled automatically. If the description or visual evidence is insufficient, leave the relevant answer blank, save a draft (including a completely blank draft if needed), and skip rather than guess. Neither assessment certifies diagnostic use or fidelity to a real patient; this is a prototype rubric, not a validated clinical instrument.

1. **“1. How well does this generated scan match the displayed description?”** — `answers.description_match`
	- Definition: Consider whether the described findings are present or absent, in the correct location, and of the stated severity. Consider findings described but missing from the scan, and additional findings that contradict the description. Assess this separately from whether the scan looks realistic.
	- `matches` — **Matches:** The described findings agree with the scan in their presence or absence, location, and severity, with no contradictory findings.
	- `partially_matches` — **Partially matches:** Some findings match, but others are missing, extra, or inconsistent.
	- `does_not_match` — **Does not match:** The main described finding is absent, contradicted, or substantially different.
	- For `partially_matches` or `does_not_match`, **“1.2. What does not match, or makes matching difficult?”** offers optional multiple-choice tags in the top-level `descriptionIssues` array: `missing_finding` (Missing finding), `extra_finding` (Extra finding), `incorrect_location` (Incorrect location), `incorrect_severity` (Incorrect severity), `attenuation_or_tissue_appearance` (Attenuation or tissue appearance), and `other` (Other).
2. **“2. Is this generated scan clinically plausible for use as a trainee comparison case?”** — `answers.clinical_plausibility`
	- Definition: Consider anatomical and pathological plausibility, including tissue appearance and consistency across slices. Consider if unrealistic features could cause a trainee to misunderstand the anatomy or pathology.
	- `plausible` — Plausible, without notable unrealistic features.
	- `plausible_overall` — Plausible overall, but with unrealistic features unlikely to cause a trainee to misunderstand the anatomy or pathology.
	- `not_plausible_overall` — Not plausible overall, or contains features likely to cause a trainee to misunderstand the anatomy or pathology.
	- For `plausible_overall` or `not_plausible_overall`, **“2.2. What realism concerns did you notice?”** offers optional multiple-choice tags in the top-level `realismIssues` array: `anatomical_structure` (Anatomical structure, including airways or vessels), `attenuation_or_tissue_appearance` (Attenuation or tissue appearance), `pathological_appearance_or_distribution` (Pathological appearance or distribution), `across_slice_consistency` (Across-slice consistency), `artifacts_or_image_quality` (Artifacts or image quality), and `other` (Other).

Issue tags are optional even when their section is shown. An unselected tag or empty array means **not selected**, not that the feature is normal or the concern is absent. Sections remain hidden until their qualifying parent answer is selected. Changing that answer to a non-qualifying choice clears the section's selections in the UI; the server rejects nonempty issue arrays without a qualifying parent answer rather than silently discarding them.

- **Comment policy v2:** A substantive comment is required to finalize **except** when `description_match` is `matches` **and** `clinical_plausibility` is `plausible`. In particular, `plausible_overall` does not waive the comment requirement. Explain what is missing, extra, inconsistent, or unrealistic; whitespace or slice markers alone are insufficient. Comments are limited to 10,000 characters. Removable 1-based slice references are optional and may refer only to successfully loaded slices; a reference is a locator, not a measurement or annotation.
- Every new save records `rubricVersion: 4`, `commentPolicyVersion: 2`, both issue arrays, and a full `rubricSnapshot` of the question objects, including their IDs, wording, definitions, choice values/labels, and conditional issue fields/questions/triggers/options. Earlier assessments retain their original rubric and policy; they are not reinterpreted or retroactively invalidated.
- Drafts autosave after 650 ms, or use Save draft. Navigation waits for pending saves; unsaved edits warn on tab close. Finalize explicitly confirms both v4 answers. Having no successfully loaded image, or any unresolved load error, blocks finalization; neither becomes an automatic negative answer. Retry the failed slice successfully, or save a draft and skip. A failed slice must actually be retried; loading another slice does not clear its failure. Partial successful loading is disclosed and recorded, but does not require loading every slice before finalization.
- Distinct successful frame requests and observed errors are counted. They are **not** evidence of visual inspection; historical errors remain after a successful retry, but resolved failures no longer block finalization. Unsaved viewing-only progress is session-local. Final reviews remain editable; edits create a draft revision. Optimistic revision checks reject conflicting tabs rather than silently overwrite them. Use one reviewer/tab.

## Private storage and audit

The ignored private directory retains the sealed cohort and prompt metadata. UID/path linkage and individual prompt event IDs/keys/timestamps stay private; the browser receives neutral titles, the intended description and distinct input texts/counts, rubric, and ratings, but no raw UIDs or paths.

Production saves go through the Mac Node server to **genai-radiology / afrooz-review**. Deterministic top-level documents named `${manifestHash}--${caseId}` contain the latest assessment; their `revisions` subcollection retains **full immutable records for every saved revision**, not just answer differences. Records include timestamp, manifest hash, rubric version and definitions, full `rubricSnapshot` for v4, comment policy version, prompt provenance, answers, issue arrays, comments (required for the final-answer combinations above), slice references, and load evidence. Updating the latest document does not overwrite earlier revision records.

Only current-rubric draft/final assessments count toward the review UI's progress. Older rubric records are marked **Needs v4 assessment** and appear in a **Previous assessment · read-only** panel with their original answers, comments, slice references, saved date, rubric version, status, and revision number. The separate new v4 form is **not prefilled** with those answers, comments, or references; both questions must be reassessed independently, without converting old Yes/No answers to v4 categories.

When a v4 assessment is first saved over an older rubric record, the server derives a `previousAssessment` snapshot from the **server-loaded prior record**, never from the submitted request body. It retains the original answers, comments, references, saved date, rubric/revision/status, and available definitions, rubric snapshot, comment policy, and confirmation fields. Subsequent v4 updates carry forward that same snapshot, so the read-only previous assessment remains available after saving and editing v4. This snapshot supplements, rather than replaces, the complete immutable revision history.

The server obtains and refreshes access tokens using `gcloud auth print-access-token --quiet`. Keep a **valid gcloud login** on the Mac with the necessary Firestore permissions; expired/revoked login or missing permissions prevents saves. Credentials/tokens stay server-side: **no browser Firebase keys, Firebase client SDK, or opened Firestore rules** are needed. Do not loosen rules to fix server IAM/login failures. A successful response means storage accepted the save; errors remain visible. This is still a shared single-reviewer workflow, not individual identity verification, an electronic signature, or a tamper-proof audit system.

### Historical paper analysis and overview

The private confirmation notebook now has a **v4-aware overview and selected-case history**, with new ratings, issue tags, comments, references, saved rubric snapshots, and separate previous-assessment columns. Run authentication (cell 2), then overview/helpers (cell 4); the **Rubric v4 results** section at the bottom reads a fresh cohort snapshot and summarizes only complete, consistent, explicitly confirmed v4 finals. Its final cell runs in-memory synthetic checks without cloud calls. The original paper figures/exports remain explicitly **v3-only**: never pool or recode v4 ratings into Yes/No results. Those old plots read latest records only, so a v4 latest record displaces that case from their v3 denominator; use a fixed historical snapshot for reproducible pre-v4 analysis. All notebook cloud operations are read-only.

### Prior journal migration (explicit operator action only)

The prior local assessment journal is an **immutable backup** after migration: retain and protect it; production Firestore mode makes **no future writes** to it. Do not rebuild the frozen cohort. Migration is not automatic and must be completed and verified by the operator before relying on prior assessments in Firestore:

- `node review-app/migrate-assessments.mjs --check` validates the sealed local source only, without credentials, Firestore access, or writes.
- `node review-app/migrate-assessments.mjs --apply` explicitly migrates validated records to Firestore; requires the server-side gcloud login and permissions. The source journal is unchanged.

These commands are operational instructions, not a claim that migration has run. Protect and back up the private directory; never commit/share it. Imported `startServer()` defaults to local journals for isolated tests; test ratings use the separately ignored test directory and are removed after tests. The UI uses `/api/session` storage metadata, not whether the page is local or hosted, to label saves.

## Known limitations

No PACS, segmentation/overlays, comparison images, export UI, verified original model prompts, validated presentation state, VOI LUT table/nonlinear presentation support, enhanced multiframe per-frame functional-group transforms/orientation, color viewing, or compressed codec installation. Unsupported decodes are flagged; enhanced DICOM with per-frame transforms is rejected rather than shown using potentially wrong transforms. Spatial gaps and instance ordering do not prove complete acquisition. Source headers/pixels may already be synthetic or altered, and source pixel changes under the same identifiers are not detected. Final status means a reviewer confirmed the form, not that every slice was inspected. Firestore, credentials, network access, or local test storage can fail; save failures remain visible and block navigation until resolved. This prototype does not replace a validated clinical viewer or institutional privacy/security review.
